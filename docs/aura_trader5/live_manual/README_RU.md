# AURA LIVE MANUAL TRADER 5.0

Дополнение PR #62: [два профиля и полный WAIT audit](profiles/REPORT_RU.md).
Консервативный сохраняет прежние сигналы; умеренный — отдельная экспериментальная
гипотеза. Переключатель не меняет серверные риски и не отправляет ордеры.
Расширенные результаты: 124800 минутных наблюдений, оба профиля без сделок,
независимого OOS нет. Условные планы при WAIT — не разрешение входа.

Изолированная ручная виртуальная торговля BTCUSDT Bitget USDT-M Futures.
Сигнал никогда не открывает позицию. Пользователь отдельно переносит план,
вводит BTC, нажимает BUY/SELL и подтверждает действие. CLOSE тоже требует
явного нажатия. Сервер автоматически проверяет только защитное закрытие уже
существующей виртуальной позиции. Реальных биржевых заявок нет.

## Где находится интерфейс

Главная страница `/`: основной LIVE-график с существующими SVG-инструментами
Фибоначчи, линиями, зонами и планом Entry/SL/TP. Под графиком — новый блок
**AURA LIVE ANALYST**, непосредственно за ним раскрываемая **Manual Paper**.
Прежний **AURA ANALYST · закрытые свечи** остаётся ниже для сравнения.

LIVE-аналитик и график работают без входа в счёт. Баланс, история, GET quote,
OPEN/CLOSE требуют существующую авторизацию владельца (`aura`, серверный пароль).
Ссылку входа содержит панель Manual Paper. Ни одного ключа биржи в браузере нет.

## Данные и причинность

Официальные публичные Bitget REST `/api/v2/mix/market/candles` и WebSocket
`wss://ws.bitget.com/v2/ws/public`, `instType=USDT-FUTURES`, `instId=BTCUSDT`.
Один новый браузерный socket ручного модуля: ticker и candle1m/5m/15m/1H/4H.
Начальная REST-история — 201 свеча/таймфрейм. Подтверждённый реальным публичным
ответом первоначальный WS snapshot содержит 500 строк: допустим ограниченный
пакет до 1000, в расчёте сохраняется только 201. Размер сообщения ≤1 MiB.

Проверяются UTC/шаг, непрерывность, конечные OHLCV, диапазон, неотрицательный
объём, отсутствие отката high/low/volume/open и изменений удерживаемых прошлых
свечей. При расхождении — STALE, остановка рекомендаций и новый REST snapshot;
нет подмены исходной истории Active43. Пропуски не заполняются искусственно.

Bid/ask и receipt не старше 5 секунд; envelope и все frame updates не старше
10 секунд. Будущие данные блокируются. Часы устройства должны быть корректны.
Начальная REST-история сама по себе не даёт LIVE: нужны WS-данные всех пяти
таймфреймов и ticker. Повтор — backoff 1–30 секунд. Abort, generations и отмена
таймеров исключают старые callbacks после смены подключения. Фоновая вкладка
отключает feed; возвращение/Android lifecycle/BFCache требуют REST resnapshot.

Расчёт и обновление DOM ограничены 2 Hz. Одна и та же формирующаяся свеча
обновляет OHLCV и визуальные EMA. Тренд/уровни/структура/swing и RSI-дивергенции
подтверждаются только уже закрытыми свечами. Pivot виден только после закрытия
двух следующих свечей. У текущей свечи подтверждение всегда **предварительное**.
Объём сравнивается с историческим объёмом с поправкой на прошедшую часть 5m
(минимальная доля 0,1); это эвристика, не прогноз конечного объёма.

## Правила LIVE-аналитика

Зафиксированы в `research/live_manual/protocol.json` до реального replay.
Закрытые 5m/15m/1h EMA20/50 должны совпасть, 4h не противоречить. Текущая 5m:
EMA-направление, RSI 52–68 LONG / 32–48 SHORT, совпадение EMA20 с прошлым
15m Fibonacci 38,2–61,8%, тело/моментум отскока, MACD и частичный объём.
SL за недавним экстремумом/1,5 ATR, TP ограничен прошлым экстремумом и 2,5R;
net R/R ≥1,5 после моделируемых расходов. Отсутствие любого условия = WAIT.
1m — краткосрочный контекст, не дополнительный обязательный входной фильтр.

Поддержка/сопротивление, MACD, структура и дивергенции показаны с совпадениями и
противоречиями, без выдуманной вероятности прибыли. План может исчезнуть при
следующем обновлении. Отмена: устаревание, выход из зоны, потеря согласования,
нарушение SL. История смены состояния/причин: последние 100 записей в памяти
вкладки, сбрасывается при reload; журнал исполненных виртуальных сделок — в БД.

Аналитическая модель консервативнее ledger: fee 0,10%/сторону, slippage 0,05%,
текущий spread. Entry уже использует сторону bid/ask, второй половины spread
на входе нет; для ориентиров выхода spread учитывается консервативно.
Manual Paper: fee 0,06% + slippage 0,05%/сторону от серверных bid/ask.
Funding и глубина стакана не включены. Это две явно разные модели, не реальные
account-specific комиссии или гарантия исполнения.

## Manual Paper и серверные ограничения

Отдельный начальный виртуальный баланс 10 000 USDT; одна позиция; номинал ≤2000;
fee-inclusive риск с проскальзыванием при SL ≤0,5%; дневной риск ≤2% от начала
UTC-дня; запрет новых входов при потере 10% исходного капитала. Дневной baseline
восстанавливается из неизменяемой истории, без дневного reset или пополнения.
Гэп может превысить расчётный риск — убыток не обрезается искусственно.
Консервативная paper-модель BTC: шаг 0,0001 BTC, минимум 5 USDT, шаг SL/TP 0,1.
Это не автоматическая проверка будущих изменений спецификации биржи.

Цена исполнения только с сервера: публичные GET time+ticker, проверка времени,
identity, spread, bid/ask sizes. Клиентская Entry — **редактируемый ориентир**,
не лимитная заявка и не передаваемая цена исполнения. SL/TP/quantity проверяет
сервер. Ещё одна проверка свежести происходит внутри транзакции после ожидания
lock; Supabase дополнительно проверяет свой clock при commit.

Идемпотентность постоянных request ID; конфликтующее тело с тем же ID отклоняется.
Неподтверждённое намерение хранится до POST в отдельном localStorage namespace;
после timeout/reload повторяется только тот же ID и только по нажатию пользователя.
CAS/lock, receipt и баланс/позиция/сделка сохраняются атомарно. Нет reset/topup API.
Неверная БД или повреждение журнала не заменяются новым балансом.

Серверный защитный loop каждые 5 секунд выполняется только при отдельно
настроенном Manual Paper и только закрывает существующую позицию по свежим
bid/ask. Браузер для него не нужен, но бесплатный Render может спать. SL/TP не
биржевые ордера: при сне/потере связи защита задерживается, убыток может вырасти.
Позиция и баланс восстанавливаются из постоянной БД. Непрерывность 24/7 не заявлена.

## Подготовка запуска после отдельного разрешения

В этой задаче ничего не применяется и не включается.

1. Проверить Draft PR/CI и SQL [`scripts/manual_paper_schema.sql`](../../../scripts/manual_paper_schema.sql).
   Если схема из #57 ещё не установлена, отдельно одобрить её выполнение.
   Все объекты имеют префикс `aura_manual_paper_v1_`; Active43/Practice не затрагиваются.
2. После отдельного одобрения публикации использовать существующие env имена:
   `AURA_MANUAL_PAPER_ENABLED=true`, `AURA_MANUAL_PAPER_STORAGE=supabase`,
   `AURA_MANUAL_PAPER_SUPABASE_URL`, `AURA_MANUAL_PAPER_SUPABASE_SERVICE_KEY` и
   существующий `AURA_TESTNET_VIEW_PASSWORD` (≥12 символов). Значения секретов
   только на сервере. По умолчанию Manual Paper выключен. Active43 PAPER не трогать.
3. Проверить owner login, источник LIVE, отдельный баланс и серверный state.
   Перенос сценария не торгует. Для проверки сделки потребуется отдельное
   разрешение на ручное виртуальное OPEN/CLOSE; в этой задаче production сделок нет.

Отключение нового Manual Paper флага запрещает новые ручные операции и останавливает
его защитный loop, поэтому перед будущим отключением необходимо убедиться, что его
собственная позиция закрыта. Не отключать защиту при открытой позиции. Active43
контролируется отдельно и не затрагивается.
