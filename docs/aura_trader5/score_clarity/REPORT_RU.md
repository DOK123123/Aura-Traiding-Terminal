# Aura 5: объяснимый балл, режим рынка и текущие сценарии — PR #84

Изменения предназначены только для `fix/aura5-score-clarity-current-signals`, база
`feature/aura-live-manual-trader5`. Никакого merge/deploy, SQL на hosted Supabase,
изменения Render/production/PAPER/Active43, аккаунтов, тарифов и реальных или
пользовательских виртуальных ордеров в этой задаче нет.

## 1. Найденные ошибки

- Signal Lock показывал текущий `score`, но объяснял его проверками из неизменяемого
  `initial`. После CANDIDATE → WATCH набор объясняемых условий мог отставать.
  Теперь сохраняются отдельные `current_checks`, `score_details`, последняя
  проверка и последнее подтверждение WATCH. `initial` остаётся историей.
- При потере достоверности reducer мог заменить последнюю проверенную оценку
  старой initial-оценкой. Теперь при UNKNOWN сохраняется последняя проверенная
  информация, явно историческая, без действующего плана.
- Сервер сначала выбирал 200 последних по detected_at записей: более старый
  действующий сценарий мог исчезнуть среди новых terminal-записей. Теперь
  эффективная свежесть и WATCH/CANDIDATE учитываются **до** ограничения ответа.
- UI оставлял UNKNOWN/EXPIRED/INVALIDATED основной карточкой без явного закрепления.
  Теперь при отсутствии текущего сценария показана причина отсутствия плана;
  история доступна отдельно. Ручной выбор истории закрепляет чтение; открепление
  возвращает текущий сценарий. Действующая выбранная карточка не скачет за баллом.
- Свежая котировка после тихой паузы worker >5s могла вернуть прежний WATCH без
  фиксации разрыва наблюдения. Теперь такой эпизод завершается UNKNOWN; тот же
  structural ID не оживает. Новая структура может создать новый эпизод.
- SQL RPC позволял переписать terminal-запись при корректном CAS version.
  Добавлена атомарная защита immutable terminal body под существующим version lock.
  Скрипт проверен только на disposable PostgreSQL, на hosted БД не применён.

## 2. Почему 80 / 83 повторяются

Формула сохранена: `round(100 × passed / total)` с равными весами 1.

| Семейство | Условий | Пример | Балл |
|---|---:|---:|---:|
| Trend Pullback / Breakout + Retest | 5 | 4/5 | 80 |
| Momentum Divergence | 6 | 5/6 | 83 |

Это дискретная шкала, а условия коррелированы. Нет вероятностной калибровки.
В UI видны ✓/✗, фактические/требуемые значения, вес, полученные/возможные баллы
каждого условия. Исходные веса, rounding и 70/65 admission/retention не подбирались.
Вклад каждого условия = 100/N либо 0; округляется итог, не порог допуска.

Даже 100/100 не означает WATCH: обязательны свежесть, все условия, геометрия,
зона входа, stop/target horizon и Net R/R после расходов. CANDIDATE не получает
Entry/SL/TP и не превращается в WATCH только по баллу. Причины отсутствия плана
показываются отдельно. WATCH остаётся технической непроверенной гипотезой,
`NO_EDGE_FOUND`; балл не представлен как вероятность прибыли.

## 3. Режим рынка — отдельный от балла

`AURA5_REGIME_V1`, ровно 260 непрерывных закрытых свечей. Для каждого 5m/15m/1h/4h
возвращаются state, причины, closed_at, показатели и фиксированные правила.
ADX измеряет силу, направление определяется независимо по EMA и high/low.

| Проверка | Правило и происхождение |
|---|---|
| ADX14 | Wilder TR/+DM/-DM, сглаживание 14; ties DM=0; первый ADX после 27 индексов |
| Сильный / слабый ADX | ≥25 / ≤20, между ними серая зона; распространённая техническая конвенция, не оптимум BTC |
| EMA | EMA20/50, знак разницы с deadband 0.1 ATR из прежнего explainable правила |
| Наклон | `(EMA20[-1]−EMA20[-6]) / (5×ATR14)`; deadband 0.1 ATR/бар — явно фиксированная описательная конвенция |
| Структура | max(high)/min(low) двух непересекающихся закрытых 10-барных блоков: HH/HL, LH/LL либо mixed/equal |
| Эффективность | `abs(C[-1]−C[-21]) / sum(abs(diff(C[-21:])))`; граница 0.3 из существующего описательного Hunter regime |
| Диапазон | high/low 20 закрытых свечей, ширина/ATR, нахождение close внутри прежнего 20-барного диапазона |

TREND_UP/DOWN: ADX≥25, эффективность≥0.3 и согласованные знак EMA-gap, наклон
за deadband и структура соответствующего направления. RANGE: ADX≤20, плоский
наклон, эффективность<0.3, mixed/equal структура и close внутри прежнего диапазона.
Иначе TRANSITION. Недостоверные/неполные/устаревшие/формирующиеся данные или
нулевой ATR → UNKNOWN. Свежесть quote для живого API остаётся обязательной.

При RANGE добавляется запрет только для Trend Pullback, отдельно для LONG и
SHORT; Breakout и Divergence продолжают собственные обязательные проверки.
Это **не бонус к баллу**. Снижения порогов, автоподтверждения и подбора весов нет.
Правила покрыты тестами и причинным архивным аудитом, но **не квалифицированы
как прогнозный или прибыльный фильтр**. Большая доля TRANSITION — честное
несогласие показателей; UNKNOWN не используется как синоним боковика.

[Справочник ADX и Wilder](https://chartschool.stockcharts.com/table-of-contents/technical-indicators-and-overlays/technical-indicators/average-directional-index-adx).

## 4. Signal Lock и отображение LONG / SHORT

Две независимые карточки и четыре таймфрейма. WATCH, затем CANDIDATE, затем
история. При отсутствии действующего сценария — явный пустой текущий статус,
а не вчерашний UNKNOWN. Ручное закрепление исторической записи и раскрытые
детали переживают reload; повторные тики не заменяют узлы карточек.

`detected_at`, `last_evaluated_at`, `last_confirmed_at` показываются отдельно.
Для старых записей без current_checks UI честно пишет, что разбивки нет, вместо
выдачи initial за текущую проверку. Терминальные карточки имеют исторический балл.
Смена структуры и достижение уровней locked plan имеют разные причины отмены.

ID зависит от модели, стратегии, стороны, TF и закрытых structural anchors,
не от котировки/score/tick. `market_regime.py` входит в MODEL_HASH: новая модель
имеет новую идентичность; завершённые старые эпизоды не изменяются. При рестарте
worker сначала закрывает необозреваемый разрыв UNKNOWN. Immutable history и
idempotent event/outbox сохраняются в отдельном private signal journal.

## 5. Историческая проверка без будущих данных

Воспроизводимый runner: `python -m scripts.audit_aura5_regime --output work/audit.json`.
Baseline — исходный коммит PR #84 `2317fe129bb6d2f3f803df7ac92b88a58a7177f7`.
Источник и SHA-256 архивов, исходный source digest, новый MODEL_HASH, правила,
каждая сторона/стратегия/TF и все cost stresses сохранены в [JSON](historical-audit.json).

Каждое решение использует только закрытый префикс 260 баров; будущая свеча не
входит в индикаторы, pivots или классификацию. Следующий реальный open читается
только после решения для расчёта гипотетического исхода. Stop-first при ties,
неблагоприятный gap по stop, проверка next-open entry zone и Net R/R.

| TF | Закрытых решений | TREND_UP | TREND_DOWN | RANGE | TRANSITION | WATCH до → после |
|---|---:|---:|---:|---:|---:|---:|
| 5m | 2017 | 128 | 173 | 198 | 1518 | 0 → 0 |
| 15m | 11261 | 862 | 737 | 1265 | 8397 | 0 → 0 |
| 1h | 2621 | 234 | 156 | 249 | 1982 | 1 → 1 |
| 4h | 461 | 54 | 18 | 52 | 337 | 0 → 0 |

Всего 16 360 префиксов / 98 160 оценок; **0 изменений технического балла**.
На этом архиве новые RANGE-ограничения не убрали дополнительных WATCH: прежние
условия уже блокировали соответствующие сочетания. Это не доказательство
бесполезности или полезности нового режима на будущих данных.

Распределение повторений: 80 встречается 5417 раз, 83 — 2647, 100 — 1065.
Всего один допустимый WATCH показывает, почему высокий балл не заменяет risk gates.
Единственный 1h исход — TIMEOUT, модельный net R −0.67157; при расходах ×1.5 / ×2
соответственно −0.70374 / −0.73014. Частота и результаты до/после совпадают.
Комиссия 10 bps/сторона, slippage 5 bps/сторона, spread 2 bps и funding-reserve
1 bps/8h — модель из существующего кода, не тариф аккаунта и не исторические bid/ask.

5m — отдельный native-архив 2026-10-25 22:45–2026-11-02 20:25 UTC;
15m — 2026-07-01–2026-10-29 UTC; 1h/4h агрегированы только из полных 15m групп.
5m из 15m не создавался. Архивы ранее исследовались, независимого OOS нет.
Наблюдения перекрываются; это не портфельная доходность и не сделки терминала.
Вердикт **INSUFFICIENT_EVIDENCE**, прибыльность не доказана.

## 6. Проверки, review и ограничения

- Unit/regression: флэт, up/down, transition, неизвестные/неполные данные;
  независимые ADX-reference 100/0, каузальность и запрет forming/future/gaps;
  шесть кандидатов LONG/SHORT на каждом TF; неизменность балла и сумма вкладов.
- Service/reducer: 500 тиков, current-vs-initial, current-first при 200+ history,
  specific absence reason, freshness API, silent worker stall, замена структуры,
  locked plan, restart, terminal states и отсутствие оживления прежнего ID.
- Реальный одноразовый PostgreSQL: RLS/роли/CAS, история/outbox dedup, рестарт,
  запрет перезаписи UNKNOWN/EXPIRED/INVALIDATED и сохранение wallet scope.
- Chromium desktop/Pixel7: 500+ обновлений, обе стороны и четыре TF, стабильные
  узлы/позиция/scroll/details, история/ручной pin/reload, четыре режима, ноль JS
  exceptions и POST. Это локальные transport fixtures, **не hosted LIVE**.
- Полный JS: 458 PASS/0 skips; targeted Python: 63 PASS; disposable Signal Lock PostgreSQL PASS. Все 10 существующих browser suites прошли (последняя chart-фикстура после исправления часов). Полный Python выполняется; точный commit,
  итоговые количества и ссылки CI фиксируются в итоговом комментарии PR #84.

В существующей chart browser-фикстуре устранена зависимость от wall-clock задержек: часы replay и timestamps событий теперь управляются согласованно. Реальные freshness-пределы приложения не менялись.

Code/security review: источники/свежесть/mandatory gates сохранены; новые данные
только текстом через textContent; нет секретов в API/логах/fixtures; нет новых
exchange методов, аккаунтов, runtime dependencies или торговых вызовов.
SQL-guard выполняется под существующим глобальным CAS-lock, роль/security invoker,
RLS и private schema не ослабляются. Нерешённых critical/high в изменённом коде
по выполненному review не выявлено; это не независимый внешний аудит.

Остаточные ограничения: ADX запаздывает; границы описательные, не оптимизированные;
исторической квалификации недостаточно. Пауза >5s завершает старую структуру до
новой идентичности — это консервативная доступность. Сохраняются лимит 5000 записей,
200 в основном ответе плюс выбранные, отсутствие гарантии 24/7 на Render Free.
SQL-guard потребует отдельного разрешённого применения при будущем выпуске;
**в этой задаче он не применялся к существующему Supabase**. Merge/deploy запрещены.
