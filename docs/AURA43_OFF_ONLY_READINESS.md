# Aura 4.3: read-only проверка Cloudflare off_only

## Где открыть после публикации

В Owner Panel над **AURA 4.3 ACTIVE PAPER v3 · BITGET FUTURES** находится
отдельная, раскрытая по умолчанию карточка **AURA 4.3 · Готовность Cloudflare off_only · только чтение**.
Прямой адрес: [открыть карточку](https://aura-traiding-terminal.onrender.com/#active43-off-readiness).
Внутри основной панели Aura 4.3 под заголовком есть ссылка «Готовность Cloudflare off_only · только чтение — перейти к проверке».
Ссылка только прокручивает страницу, не вызывает API.
Войдите через «Вход владельца» с существующей авторизацией и нажмите
**ПРОВЕРИТЬ OFF-ONLY БЕЗ ИЗМЕНЕНИЙ**. Раскрывать обычную торговую панель для этого не требуется.

Блок показывает сохранённый режим OFF/ON/PAUSED/EMERGENCY, количество позиций,
наличие pending/pending_exit, количество ожидающих операций, data_recovery_armed,
результат production risk guards, UTC-время успешного чтения и PASS/BLOCKED.

## Что означает результат

PASS означает только проверенные предпосылки пустого OFF-счёта для `off_only`:
валидное состояние отдельного Bitget-счёта, ноль позиций и ожидающих операций,
отключённое восстановление данных, отсутствие отказа существующего `risk_reason`,
готовый серверный модуль и настроенная авторизация scheduler.
Risk guards проверяются на сохранённом состоянии без изменения дня, equity или лимитов.

Это снимок, а не блокировка счёта: после чтения состояние может измениться.
Через 60 секунд интерфейс заменяет PASS на BLOCKED и предлагает повторить чтение.
Сам `off_only` повторно проверяет свои ограничения в существующем серверном пути.
PASS не доказывает работу Cloudflare, доступность Bitget или непрерывность Render,
не включает Cron/PAPER и не подтверждает production OPEN → CLOSE.

BLOCKED с неподтверждёнными полями означает отсутствие авторизации, счёта,
полных/валидных данных либо ошибку чтения. Отсутствующие поля никогда не заменяются нулём.
Причины серверных отказов передаются только фиксированными кодами; браузер выводит
безопасные сообщения через textContent. Ошибки подключения не сохраняют прошлый PASS.

## API и отсутствие записей

`GET /api/active43/off-only-readiness` использует существующую owner HTTP Basic
авторизацию и заголовки no-store/nosniff. Scheduler token не заменяет owner-доступ.
POST недоступен. Неавторизованный запрос получает 401/403 и в UI даёт BLOCKED.
Авторизованные запросы возвращают HTTP 200 с явным status=PASS/BLOCKED.

Выполняется только `Store.peek()` — существующий ограниченный GET к
`aura_active43_bitget_account` с проверкой checksum, модели, scope и конфигурации.
Нет вызовов load/seed, RPC-записи, history, tick, initialize или торговых команд.
Когда модуль выключен, возможен только credential-only fallback того же peek;
его собственный HTTP-клиент закрывается, а итог остаётся BLOCKED.
Каждое нажатие читает БД заново; кэш общей diagnostics не используется.
В браузер не передаются баланс, параметры позиции, ID сделок, payload счёта,
ключи, секреты или raw-ошибки БД.

Новый блок расположен отдельно от существующей панели: её `/status` использует
load и поэтому намеренно не вызывается новой диагностикой. Другие ранее открытые
панели и независимый scheduler не останавливаются; проверка не претендует на
блокировку всех прочих действий терминала.

## Публикация

Нужны только обычные owner-approved Merge и Render Deploy этой ветки.
SQL-миграции, новые env, платные ресурсы и изменение секретов не нужны.
Эта разработка не выполняет Merge/Deploy, не включает PAPER или Cloudflare.
После публикации проверьте новый блок, оставив торговые команды нетронутыми.

## Воспроизводимые проверки

- `python -m pytest -q tests/test_active43_readiness.py`
- `node --test tests/test_active43_readiness_frontend.cjs`
- `AURA_ACTIVE43_VERIFY_POSTGRES=true python -m pytest -q tests/test_active43_postgres.py`

PostgreSQL-проверка использует отдельный локальный контейнер и фиктивные данные,
существующий Store/HTTP endpoint, проверяет owner-авторизацию и три конкурентных GET.
Сериализация строк счёта и журнала до/после должна совпасть байт-в-байт.
Этот тест не обращается к production Supabase и не доказывает работу Render.

## Code review и security review

Проверены отдельными проходами по `docs/ecc/TRADING_REVIEW.md`:

- Code review: endpoint вызывает только peek; validate/risk_reason/ready проверяют
  состояние без переходов. Нет изменения engine, scheduler, SQL, Store или risk
  thresholds. Блок отделён от legacy status/load, не запускается по раскрытию.
- Security review: owner dependency до чтения, no-store/nosniff, нет новых
  write-методов или credentials в ответе. Ошибки проходят allowlist, UI использует
  textContent, прошлый PASS удаляется при ошибках и по истечении TTL.
- Критических/high замечаний по изменению не обнаружено. Ограничения: read-only
  снимок не исключает изменение счёта другими процессами после чтения; реальный
  Render и owner browser после публикации требуют отдельной проверки.

## Исправление видимости после PR #25

22 октября 2026 проверен объединённый PR #25, main
`d0954f2efb5c84a3b6ed8f42392a9886999b1598` и публичные статические файлы Render.
`GET /` и `GET /static/active43-readiness.js` вернули содержимое, побайтово
совпадающее с main. HTML SHA256:
`16c592355397bc3d1cc0e3da8964c448959f17793bfe998ba15ffe27c60be60e`.
Это подтверждает актуальность этих двух файлов, а не SHA всего серверного кода.
Торговые API, production Supabase и Cloudflare не вызывались.

Причина неудобства: карточка была отдельным свёрнутым `<details>` **перед**
`#active43-panel`; внутри основной панели ссылки на неё не было. Кнопка
скрывалась стандартным поведением закрытого details. У readiness-карточки также
не было оформления Aura 4.3: существующий CSS ограничен `#active43-panel`.
Ни авторизация, ни настройка PAPER, ни JavaScript не определяли видимость каркаса.

Исправление: отдельная карточка раскрыта по умолчанию, получила собственные
локальные стили, а внутри Aura 4.3 непосредственно под заголовком добавлен якорь
«Готовность Cloudflare off_only · только чтение — перейти к проверке».
Карточка остаётся sibling, чтобы её открытие не запускало legacy status/load.
Загрузка страницы и переход по ссылке не выполняют readiness-запрос.
Новые JS, SQL, env, backend и торговые операции не добавлены.

Локальный Chromium на мобильном viewport 390 px подтвердил:
старый main — details закрыт, кнопка невидима; исправление — details открыт,
кнопка видима, ширина карточки 366 px, основная торговая панель закрыта.
До нажатия не было readiness GET; после нажатия был ровно один запрос.
Изолированный HTTP 401 даёт BLOCKED. Браузер работал с локальным static-only
сервером без БД; публичная сеть заблокирована proxy. Это не проверка owner login
на production и не чтение реального портфеля.

Code/security review исправления: изменения только HTML, scoped CSS и тестов;
auth/read-only API неизменны, новых вызовов/секретов нет. Критических/high
замечаний не обнаружено. Проверка исправления на Render возможна только после
отдельной публикации владельцем; Merge и Deploy в рамках задачи не выполняются.

Проверки исправления видимости: полный Python suite — **1556 passed, 3 skipped**
за 110,69 с (три существующих PostgreSQL opt-in теста не включались; SQL/backend
не менялись); полный Node suite — **227 passed**. AST 230 Python-файлов,
import app.main, node --check, diff --check — PASS. Chromium проверка — PASS.
