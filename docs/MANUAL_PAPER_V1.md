# Manual Paper v1 — отдельный виртуальный счёт

Начальный баланс: **10 000 USDT**. Одна LONG/SHORT-позиция BTCUSDT USDT-M.
Никаких реальных ордеров, биржевых ключей, переводов или подключения к Active43.
Модуль выключен по умолчанию и не переключает автоматический PAPER.

## Что реализовано

- Owner Basic Auth (`aura`, существующий серверный `AURA_TESTNET_VIEW_PASSWORD`, минимум 12 символов).
- Защита изменений: `X-Aura-Paper: local-only`, проверка Origin и Sec-Fetch-Site.
- Клиент передаёт только сторону, BTC-объём, SL, TP и ID запроса. Клиентская цена запрещена схемой API.
- Сервер запрашивает публичное время Bitget и `GET /api/v2/mix/market/ticker`, строго BTCUSDT/USDT-FUTURES. Другого провайдера и запасного источника нет.
- Вход LONG по ask, SHORT по bid; выход LONG по bid, SHORT по ask. Это учебная модель исполнения по лучшей цене, не биржевое исполнение.
- Проверяются часы, `requestTime`, `ts`, положительные конечные bid/ask/размеры, непротиворечивый спред. Котировка не старше 5 секунд; повторная проверка производится внутри транзакции перед изменением баланса.
- Максимум 2000 USDT на позицию, одна позиция, риск до SL с обеими комиссиями ≤0,5% текущего баланса. Новые входы блокируются при балансе ≤9000 USDT (падение на 10% от начального капитала). Комиссия 0,06% на каждую сторону.
- Баланс, позиция, история и постоянные квитанции запросов записываются одной SQLite-транзакцией (`BEGIN IMMEDIATE`, WAL, synchronous=FULL).
- Повтор того же ID/намерения возвращает исходную квитанцию, даже если котировка изменилась или Bitget недоступен. Числа `0.01` и `0.010` означают одно намерение. Другое намерение с тем же ID отклоняется.
- Закрытие привязано к ID позиции: старый запрос не может закрыть новую позицию.
- Квитанции защищены триггерами от UPDATE/DELETE; неверный баланс/математика журнала и исчезнувшее состояние при существующих квитанциях блокируют работу вместо сброса счёта.
- Защитный цикл сервера проверяет существующую позицию каждые 5 секунд плюс время HTTP/БД. Цикл не открывает позиции и не обращается к Active43. После перезапуска он продолжает сопровождение сохранённой позиции.
- Мобильная панель: LONG/SHORT, BTC-объём, SL/TP, баланс, equity, net PnL, позиция, пагинированная история и ошибки защиты. Неизвестный исход запроса сохраняется в localStorage до отправки; кнопка повтора использует тот же ID после перезагрузки страницы.

## Постоянное хранение и конфигурация

На Render допускается **только реально смонтированный постоянный диск**. Просто задать путь недостаточно: проверяются mountpoint, путь внутри него и отсутствие подмены через symlink перед каждым подключением к SQLite. Если проверка не пройдена, операции блокируются. На обычном временном диске Render баланс не создаётся.

После отдельного разрешения на развёртывание:

1. Подключить постоянный диск к сервису с mount path `/var/data`.
2. Установить следующие переменные (пароль владельца остаётся только в серверном окружении):

```text
AURA_MANUAL_PAPER_ENABLED=true
AURA_MANUAL_PAPER_STORAGE=persistent-disk
AURA_MANUAL_PAPER_MOUNT=/var/data
AURA_MANUAL_PAPER_DB=/var/data/manual-paper.sqlite3
```

3. Существующие переменные Active43, автоматический PAPER и scheduler не менять.
4. После запуска проверить `/api/health`, войти владельцем, открыть Manual Paper и прочитать `/api/manual-paper/state`. Требуется `storage_durable: true`, баланс `10000`, пустая позиция и история у нового счёта.
5. Без открытия сделки перезапустить сервис и сравнить сохранённое состояние. Отдельную пробную виртуальную сделку выполнять только после разрешения пользователя.

Постоянные диски Render доступны для платных экземпляров. Диск ограничивает сервис одним инстансом; при deploy есть перерыв. Диск подключается в runtime, не на этапе build. Тариф и размер здесь не назначаются и никакие покупки/изменения Render не выполнены.

Источник ограничений: [Render Persistent Disks](https://render.com/docs/disks), проверено 26.10.2026. Файловые snapshots не заменяют согласованный backup БД: использовать SQLite Connection.backup и проверять восстановление отдельно; копирование только основного файла работающей WAL-базы небезопасно.

Локальный режим для разработки:

```text
AURA_MANUAL_PAPER_ENABLED=true
AURA_MANUAL_PAPER_STORAGE=development
AURA_MANUAL_PAPER_DB=/absolute/existing/directory/manual-paper.sqlite3
```

Режим `development` запрещён при наличии `RENDER`. Он не считается постоянным production-хранилищем. Файл должен быть выделенным; база с чужими таблицами отвергается. Директория должна существовать. Счёт один, для владельца сервера. Сброса баланса и пополнения через API нет.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/manual-paper/capabilities` | Общий безопасный контракт; не доказывает готовность БД/рынка |
| GET | `/api/manual-paper/state?offset=0&limit=50` | Защищённое чтение счёта, котировки и истории; первая авторизованная загрузка создаёт пустой счёт |
| GET | `/api/manual-paper/quote` | Защищённая текущая котировка сервера |
| POST | `/api/manual-paper/orders` | Виртуальный вход |
| POST | `/api/manual-paper/positions/{position_id}/close` | Виртуальное закрытие конкретной позиции |

Вход:

```json
{"request_id":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","side":"LONG","quantity":"0.01","stop":"79500","target":"81000"}
```

Закрытие:

```json
{"request_id":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"}
```

Числа в запросах — строки с максимум 12 знаками после точки; NaN, Infinity, bool, экспоненты и лишние поля запрещены. Цены в примере учебные и не являются актуальными котировками или торговой рекомендацией.

При 5xx/таймауте исход может быть неизвестен: повторять **то же намерение с тем же ID**. 409 означает отклонённую транзакцию, 422 — неверное тело. Запросы и их ID не удаляются по сроку хранения. Конкуренция между процессами регулируется SQLite, а не только локальным asyncio.Lock.

## Ограничения модели

- Проверка SL/TP дискретная, по свежему bid/ask. При ценовом разрыве выход записывается по наблюдаемой цене, а не по выдуманной цене SL. Убыток может превысить плановый риск и даже привести к отрицательному виртуальному балансу SHORT.
- Сон, остановка процесса и недоступность Bitget/БД задерживают защитные выходы. Промежуточные касания уровней во время простоя не восстанавливаются. Отображается ошибка/время последней проверки; новые команды требуют свежих данных.
- Не моделируются funding, полная глубина стакана, очередь заявок, задержка реального исполнения и ликвидация. Проверяется доступный объём лучшей цены на входе; защитный выход оценивается по наблюдаемому bid/ask.
- Сохранённый баланс доступен при недоступном рынке; актуальная equity/PnL скрыты. Это не подтверждение доступности рынка из региона production-сервера.
- История пагинирована в API/UI, но в v1 хранится в одной транзакционной записи счёта. Это учебный один пользователь, не высоконагруженная многопользовательская биржа.
- SQLite-перезапуски проверены локально. Реальный persistent mount и публичная связь Bitget с Render проверяются после отдельно согласованного deploy.
