Дата: 14 октября 2026. База: `5a5562b8d99464ca546bc98a4ccd4783eb24db44`, актуальный `main` на момент проверки.

## Подтверждено и не подтверждено

Прослежен путь `static/market_context.js::createReader` → защищённый GET
`/api/intelligence/market-context` → `MarketContext.snapshot/refresh` →
`fetch_window` → существующий `app.lab.data.public_page` → фиксированный Binance
Spot `https://data-api.binance.vision/api/v3/klines` → проверка закрытых OHLCV →
`analyze_window` → те же `segment_states` и полные UTC 1h/4h блоки → JSON → UI.

Подтверждённые недостатки исходного кода:

1. Каждые 30 секунд после истечения кэша заново скачивалось до 4175 свечей
   пятью последовательными запросами в общем бюджете 12 секунд. Даже между
   закрытиями свечей повторялись загрузка всей истории и вычисления трёх TF.
2. Любая ошибка заменяла успешный кэш пустым ответом. Браузер также стирал
   последний успешный анализ при сетевом сбое.
3. Источник таймаута скрывался общей меткой TIMEOUT: получение и вычисление
   невозможно было различить по ответу.

Регрессионный тест воспроизводит исчерпание общего бюджета при пяти страницах
и успешное получение той же истории инкрементальным запросом. Время в тесте
масштабировано, транспорт искусственно задержан; это проверка механизма,
**не измерение скорости Binance или Render**.

Прямой сетевой диагностический запуск был прерван пользователем и не дал
достоверных измерений. Повторных сетевых попыток после возобновления не было.
Нет журналов Render, профиля Android или авторизованного live-ответа. Поэтому
DNS/TLS, cold start, upstream latency, загрузка CPU/RAM и фактический источник
каждого наблюдавшегося таймаута **не установлены**. Нельзя утверждать, что
Binance является единственной причиной или что live-проблема уже устранена.

## Изменения

- Кэшируется ограниченное исходное окно закрытых свечей в памяти процесса.
  При следующем обновлении повторно проверяется последняя известная свеча и
  загружается только новый хвост. При обычном обновлении — один GET вместо пяти.
  Сдвиг окна на границе UTC 4h сохраняет прежние правила прогрева и расчёта.
- Отсутствующий старт окна, разрыв в кэше или длительный сон требуют полной
  загрузки. Несовпадение повторной свечи отклоняется, следующее обновление
  выполняет полный resnapshot. Никаких цен из другого источника или заполнения.
- На страницу: максимум две попытки, 4 секунды на попытку включая чтение тела,
  backoff 0.25 × 2^attempt секунды; общий бюджет загрузки остаётся 12 секунд.
  Повторы только для сетевых/timeout ошибок и HTTP 500/502/503/504.
  403/451/418/429 и прочие HTTP не повторяются внутри запроса. Существующий
  Retry-After cooldown сохраняется. Поэтому холодная полная загрузка всё ещё
  может завершиться таймаутом при медленном источнике: лимиты не обходятся.
- Одна общая refresh-задача для всех трёх TF, защищённая от отмены отдельного
  HTTP-клиента, сохраняется. Неизменная подтверждённая история не пересчитывается;
  время вычисления сохраняется, время успешной проверки источника обновляется.
- Ошибки разделены на UPSTREAM_TIMEOUT и ANALYSIS_TIMEOUT. Внешний бюджет
  ожидания snapshot — 22 секунды; browser fetch/body — 24 секунды. Отмена браузером
  помечается отдельной причиной BROWSER_TIMEOUT, не объявляется ошибкой Binance.
- При ошибке текущие `state/levels/mtf` остаются недоступными, HTTP 503,
  решение WAIT и execution_enabled=false. Последний успешный ответ возвращается
  отдельно в `last_successful_analysis`, явно STALE, исключительно для просмотра.
- UI хранит последний успешный результат отдельно для каждого TF. При ошибке
  или истечении срока показывает его с предупреждением «НЕАКТУАЛЬНО» и WAIT,
  сохраняя источник, последнее закрытие и время последнего успешного обновления.
  После 401/403 браузерный кэш очищается. Ответ другого TF не принимается как свежий.
- Состояния UI: LOADING / READY / STALE_DATA / UPSTREAM_TIMEOUT /
  ANALYSIS_TIMEOUT / DATA_UNAVAILABLE / ERROR; русские тексты, data-state,
  aria-busy, блокировка повторного refresh и освобождение кнопки в finally.
- Безопасные логи: стадия, whitelist-код, HTTP status, elapsed_ms, число свечей,
  fetch_ms/analysis_ms, число страниц и повторно использованных свечей, номер retry.
  Без URL, тел ошибок, headers, credentials и сырых исключений. INFO виден только
  при разрешённом уровне логирования приложения; конфигурация Render не менялась.

## Отдельные review-проходы ECC/Aura

Architecture/Python: общий кэш остаётся ограниченным 4175 свечами; нет новой
базы, фонового polling-loop или зависимости от приватного клиента. 12/8/22/24 s
бюджеты сохранены, max 5 страниц, по 2 transport-попытки. CPU при новых данных
по-прежнему работает в thread с существующим cooperative deadline 8 s;
это не принудительное завершение зависшего native кода.

Security: owner/CSRF/replay/портфели не менялись. Единственный транспорт —
существующий публичный GET Binance. В адаптере нет account credentials и write
endpoints. Старый результат отделён от текущего state и всегда WAIT. В UI только
textContent; никаких trade activation запросов. Существующие security-тесты PASS.

Trading math/causality: исходники индикаторов, структуры, агрегирования,
стратегии, Decimal execution, sizing, SL/TP и fees не изменены. Новый путь выбирает
то же ограниченное окно, не добавляет свечи и не использует forming candle.
Старые проверки причинности, gap-reset, pivots/BOS/CHoCH/retest/sweep и MTF PASS.
Это не бэктест и не свидетельство торгового преимущества.

## Ручная проверка Render / Android

1. После фактического деплоя открыть `https://terminal.onrender.com/#market-analysis`
   с действующим owner-доступом. Фактический деплой этой сессией не проверен.
2. По очереди выбрать 15m, 1h, 4h: проверить источник Binance, UTC последней
   закрытой свечи, последнее успешное обновление, структуру/уровни/MTF.
   Отсутствующий паттерн и UNKNOWN допустимы, WAIT обязателен.
3. Несколько раз обновить в пределах одной 15m свечи: сверить серверные INFO
   fetch_pages=1, reused_candles, fetch_ms/analysis_ms. Первый cold start должен
   быть отдельным наблюдением с полной загрузкой, а не доказательством медленного API.
4. Дождаться нового 15m close и границы 1h/4h; проверить продвижение timestamps
   и появление только завершённых старших свечей.
5. Отключить интернет телефона после успешного ответа: старый анализ должен
   остаться с «НЕАКТУАЛЬНО», WAIT; кнопка должна восстановиться после ошибки.
   Вернуть сеть, обновить — свежесть только после успешного серверного ответа.
6. Проверить sleep/wake Render: честное ожидание/ограниченный timeout без вечного
   spinner. Сопоставить время браузерного запроса и стадии серверных логов.
7. Проверить ширины 320–430px, переключение TF при ожидании, скрытие/возврат вкладки.

## Остаточные ограничения

Не выполнены live Render/Android/browser, DNS/TLS/CPU/RAM profiling и реальные
Binance latency measurements. Нет обещания 24/7 на Render Free. Кэш только в памяти
одного worker, после restart исчезает; между workers single-flight не общий.
Ранняя коррекция давно закэшированной свечи обнаружится только при полном
resnapshot, как и в обычном TTL-кэше. Бесконечных retries/обхода ограничений нет.
Исторический совместимый pack 3.0 отсутствует: аналогам нельзя придумывать статистику.
Торговая стратегия и Auto Paper этим read-only анализом не управляются.
