# Active43: строгая история и готовность PAPER

Основа: main 49c36f43e8a2b04a9294359db59565f6f0be1cce.
Production-код, настройки, PAPER mode и рабочая Supabase не изменялись.
В production выполнены только публичные GET health/market, без account/controls/tick.

## Подтверждённые дефекты и исправления

1. `paper_readiness.inspect` проверял свежесть и полноту новой истории, но не
   сравнивал её с сохранённым `watermark / last_bar_hash`. Воспроизводимый тест
   возвращал READY при изменённой/отсутствующей контрольной свече. Теперь вызывается
   тот же `history_issue`, который использует trading Service: несовпадение даёт
   BLOCKED с UTC якоря, старым/новым хешем, полями изменения и причиной отказа.
2. `Service.control START` всегда устанавливал новую базовую свечу и очищал guard.
   После HISTORY_CANDLE_CHANGED последовательность STOP → START могла молча
   принять другую историю. Новый регрессионный тест до исправления не получал
   ожидаемый отказ. Теперь START сначала сравнивает существующий якорь: при
   расхождении не меняет ни mode, ни баланс, ни журнал, ни revision. Поддержаны
   LONG/SHORT, 5m/15m, changed/missing, восстановление оригинала и повторный START.
   Первый START нового счёта без якоря остаётся допустимым при остальных guards.

Контроль хеша НЕ отключён и НЕ нормализован. Дополнительно история теперь
различает `NUMERIC_VALUES_CHANGED`, `DECIMAL_FORMAT_CHANGED`, `UNDETERMINED`.
Даже `1.00` → `1` продолжает давать HISTORY_CANDLE_CHANGED и запрещает входы.
Это только диагностическая классификация, не доказанная причина конкретного
production-инцидента. Для старого счёта без сохранённых полей вывод UNDETERMINED.

Новая read-only секция Owner Panel в существующей кнопке
**«ПРОВЕРИТЬ ГОТОВНОСТЬ PAPER»** показывает сравнение истории. Отсутствие нового
history-контракта даёт BLOCKED, включая старый backend с новым JavaScript.
Старый JavaScript с новым backend также увидит BLOCKED/errors при несовпадении.
Диагностика не вызывает load/seed/adopt, tick, START/STOP или REBASELINE.
Сравнение anchor — это проверка контрольной свечи, а не доказательство неизменности
всего исторического архива; отдельно проверяется непрерывность свежего окна.

## Аудит работающего пути

Bitget Public Client → server/request timestamps → закрытые упорядоченные OHLCV
→ полное окно и digest → стратегия → history_issue → risk manager → pending
→ следующий доступный open → виртуальный SL/TP → Decimal PnL/fees → CAS commit
→ неизменяемая квитанция → owner UI. Exchange order API в этом пути отсутствует.

Проверены существующие safeguards, без изменения формул/порогов:
- BTCUSDT USDT-FUTURES, без Spot/другой биржи; timestamp freshness -3/+10 секунд;
- закрытые свечи, непрерывность/дубликаты, source digest; будущие bars запрещены;
- 0.5% риск с расходами, 2% дневной лимит, 10% drawdown guard, одна позиция,
  номинал <=2000, Bitget tick/lot/minimum; funding не моделируется;
- комиссии 10bps и slippage 5bps на сторону; неоднозначный SL/TP — SL первым;
- пропущенные циклы не порождают ретроспективные входы;
- при повреждении истории входы запрещены; уже открытая позиция сопровождается
  только отдельными свежими достоверными candles. Без достоверных данных —
  EMERGENCY_UNTRUSTED_DATA, а не исполнение по старой цене;
- возврат исходной свечи разрешает существующее armed-восстановление PAUSED;
  пользовательский OFF не возобновляется автоматически;
- deterministic slot key, SQL CAS/идемпотентность и immutable read-back receipt;
  рестарт/потерянный ответ БД не должны создавать второй OPEN/CLOSE;
- owner auth/no-store/ограниченный probe; отсутствие прав/БД/данных = BLOCKED.

История источника действительно может исправляться, а после длительного простоя
старый якорь может выпасть из ограниченного окна. Это безопасные блокировки,
а не повод автоматически заменить контрольный хеш.

## Что остаётся перед PAPER ON

**Сейчас разрешать PAPER ON на основании этой проверки нельзя.**
Нет свежего авторизованного подтверждения сохранённого OFF, баланса/позиций/pending
и двух актуальных записанных автоматических циклов. Причина конкретного старого
production HISTORY_CANDLE_CHANGED без original/new полей/хешей не установлена.

После отдельного одобрения merge/deploy:
1. Войти владельцем → «ПРОВЕРИТЬ ГОТОВНОСТЬ PAPER». Проверить OFF, существующий
   баланс (не сбрасывать), positions/pending=0, risk PASS, свежий market и history
   MATCHED или NOT_ESTABLISHED для нового счёта.
2. Если история BLOCKED: сверить timestamp/хеши/поля. При временном сбое дождаться
   возвращения исходной свечи. Если источник подтвердил исправление, только после
   отдельного решения владельца использовать уже существующую OFF REBASELINE:
   owner-auth `/api/active43/control`, action REBASELINE, expected_revision,
   уникальный request_id, confirmation `REBASELINE OFF PAPER ONLY` и штатная CSRF
   защита. Только OFF, без позиции/pending и с пройденными risk guards. Не SQL,
   не RESET, не START для молчаливого принятия новой истории. Здесь не выполнялось.
3. Подтвердить два разных автоматических TICK_SAVED/Supabase tick_id в разных
   слотах, затем отдельное разрешение на PAPER ON. Наблюдать естественный сигнал,
   OPEN/UPDATE/CLOSE и журнал; не подделывать production-сигнал.

При проблемах EMERGENCY запрещает входы, но не гарантирует мгновенного закрытия
позиции. Не отключать scheduler при открытой позиции без плана защиты. Free
Render/внешний cron не дают SLA: задержки, сон и гэпы могут ухудшить виртуальный
SL/TP и фактический убыток сверх порогов guard. Прибыльность не подтверждена.
