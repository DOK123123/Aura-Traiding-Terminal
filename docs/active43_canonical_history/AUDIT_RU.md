# Active43 HISTORY_CANDLE_CHANGED — точные числа и volume-only recovery

Основа main: 3bde68712573316dde5365096e586554482f3131 (после PR #55).
Работа локальная. Production, PAPER mode, env/ключи, Supabase, Cloudflare и реальные
средства не изменялись. В этом аудите свежие production-логи и API не запрашивались.

## Первопричины и границы доказательств

1. `Bar.data()` сохраняет scale Decimal, `digest()` хеширует текст JSON:
   `100`, `100.0`, `100.000` дают разные хеши при равных числах. Core/recovery ранее
   сравнивали только текстовый digest, поэтому формат мог вызвать ложную паузу.
   Это воспроизводимый дефект, а не утверждение, что все остановки были форматными.
2. В main есть зафиксированный production-пример 2026-10-25: timestamp 1792941900,
   close **80545 → 80550.4**, base volume **41.1909 → 41.4947**. OHLC изменилась
   численно; такую коррекцию нельзя исправить нормализацией. Fixture проверена
   тестом `test_production_incident_20261025_late_close_and_volume_revision`.
   Сам первичный production-лог здесь независимо не получен; происхождение
   подтверждено только сохранённым в репозитории fixture/описанием PR #54.
3. Публичный Bitget history endpoint отдаёт закрытую по времени свечу, но эта
   граница не доказывает неизменность последующих ответов. `bitget.py` правильно
   исключает формирующиеся свечи, проверяет UTC/порядок/цены/объём/clock freshness.
   `market.py` строит полное закрытое окно, проверяет контракт и source digest.
   Нет оснований заменять эти проверки или автоматически принимать другую цену.
4. PR #55 добавил rebaseline после трёх наблюдений *любых* числовых изменений,
   включая close. Стабильность пересмотренной цены не доказывает её безопасность.
   Это поведение сужено: автоматическое принятие OHLC запрещено.

Без свежих original/revised production OHLCV и tick ID нельзя определить долю
каждой причины во всех повторяющихся остановках. Изменённая цена и большой
пересмотр объёма по-прежнему должны останавливать новые входы.

## Реализация

Новый изолированный `app/active43/candle_integrity.py`:
- canonical decimal: fixed-point строка с удалением только дробных нулей;
- без float, округления, epsilon, `Decimal.normalize()` и зависимости от context;
- сохраняет целые нули (`100000`), приводит signed zero к `0`, ограничивает
  размер/экспоненту, отклоняет NaN/Infinity;
- canonical hash включает timestamp и все пять OHLCV полей;
- исходные `Bar.data()` и source_sha256 окна остаются сырыми/проверяемыми;
  общие модели, Aura4.2 и другие ledger hashes не меняются.

Новые anchors в core/START/explicit rebaseline/service используют numeric hash.
Legacy account читается без миграции БД: совпадение старого raw либо numeric hash
доказывает идентичность. Если legacy raw-хеш не совпал из-за формата, нужны
сохранённые исходные поля с корректным старым digest и ровно равные числовые
OHLCV/время. Без доказательства — BLOCKED, не восстановление «на доверии».
Переход legacy → numeric на том же watermark сохраняется атомарно с tick и
`HISTORY_NORMALIZED`/`EXACT_DECIMAL_EQUIVALENCE`; повторная доставка не пишет второй
результат. START/readiness используют ту же проверку, не обходят её.

## Допустимое уточнение объёма

Предлагаемая консервативная **политика качества данных**, не калиброванный допуск
Bitget и не изменение риска на сделку:

- исходные OHLC и timestamp точно равны; цена никогда не корректируется;
- старый volume >0, новый строго больше, прирост **<=0.1%**;
- граница проверяется точной рациональной арифметикой, без округления Decimal;
- три последовательных разных закрытых timeframe-слота с одним numeric hash;
- полное непрерывное свежее окно, валидные candles и контракт/источник;
- только ранее owner-started ON → PAUSED, armed-recovery; без позиции,
  pending/pending_exit, emergency, risk block и завершённых сделок;
- explicit OFF не возобновляется; повторный tick в том же слоте не учитывается;
- изменение кандидата, пропущенный слот, gap/ошибка API сбрасывают подтверждение.

Только после этих условий существующий flat-only recovery пропускает весь
карантинный интервал, очищает pending/старые сигналы и ждёт следующую свечу.
Нет ретроспективных сделок. `HISTORY_REBASELINE` содержит volume-only причину,
поля допуска, исходный/новый хеш, интервалы и число наблюдений.
Уменьшение volume, рост >0.1%, нулевой исходный volume, неизвестная исходная свеча,
любое изменение open/high/low/close остаются BLOCKED и требуют расследования
или существующего отдельного owner-confirmed OFF REBASELINE.

Позиции при сбоях по-прежнему сопровождаются отдельным проверенным свежим
protection window. Уже обработанные свечи не исполняются повторно. При отсутствии
достоверных свежих данных нельзя исполнять SL/TP по старой цене.

## Тесты и политика обновления fixtures

Старые tests, требовавшие блокировать доказанно равные Decimal или разрешать
авто-принятие close после трёх слотов, обновлены под явно изменённое требование.
Их защита не удалена: добавлены отрицательные тесты OHLC на пяти последовательных
слотах, большие/уменьшившиеся объёмы, missing, неподтверждённый legacy, точная
граница >0.1%, восстановление после restart, повторный tick и сбой источника.
Положительные quarantine fixtures теперь используют +0.01 на volume=100
вместо прежнего +1, то есть соответствуют новому ограниченному допуску.

Регрессионные результаты и PostgreSQL-доказательства: `results.json` рядом.
Только изолированные synthetic scenarios; это не production paper verification.
Риск 0.5%, дневной лимит 2%, drawdown 10%, одна позиция, комиссии и SL/TP формулы
не менялись. Реальных/private exchange order методов не добавлено.

## Безопасный выпуск и откат

1. Review PR/CI, отдельно разрешить merge/deploy. В production ничего из этой
   задачи не применено. SQL-миграции и смена env не нужны.
2. Оставив PAPER OFF, выполнить существующую owner read-only PAPER readiness:
   проверить сохранённый счёт/позиции/pending, свежесть окна, сравнение EXACT_NUMERIC_V1.
   Это не разрешение включить торговлю. Если старая запись hash-only не даёт
   доказательства numeric identity — диагностика должна остаться BLOCKED.
3. После отдельного разрешения PAPER наблюдать натуральные tick: форматные
   эквиваленты не должны паузить; малый volume идёт через три проверки;
   OHLC-коррекция обязательно PAUSED. Не создавать искусственные production-сигналы.

Откат только после отдельного разрешения, OFF и отсутствия позиций/pending.
Старый binary может не понимать новый numeric hash и безопасно приостановиться.
Не восстанавливать БД из старой копии и не переписывать хеши SQL. При откате на
#55 не включать PAPER: его более широкое принятие OHLC не соответствует новой
политике. Legacy accounts/баланс/история должны оставаться на месте.

## Code/security review

Проверяются точные числовые равенства, доказательство legacy-хеша, безопасные
границы чисел и независимость от Decimal context. Цена не принимается ни при
каком числе повторов. Source freshness, owner auth, CAS/atomic journal, risk
policy и OFF intent сохраняются. Финансовое исполнение и shared ledger модели
не меняются. Остаточные ограничения: неизвестны текущий production account и
частота исправлений Bitget; 0.1% — консервативная предложенная граница, а не
обещание устранить все паузы. Free hosting не даёт SLA/непрерывных virtual stops.
