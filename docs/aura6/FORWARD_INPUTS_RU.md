# Aura 6: точные входы и диагностика наблюдателя

Продолжение 30 октября 2026. Этот этап исправляет достоверность входов и готовит проверяемый сбор наблюдений. Вердикт исследований остаётся NO_EDGE_FOUND. Новые параметры стратегий не подбирались; engine.py, rules.json, архивы и сохранённые метрики не изменены.

## Подтверждённые дефекты и исправления

- Запрос 260 native баров мог включать текущую формирующуюся свечу. После её удаления оставалось 259, а код принимал даже 250. Теперь запрашивается 261, перед анализом требуется ровно 260 закрытых непрерывных баров и актуальный cutoff. Формирующиеся бары исключаются. Математика индикаторов не изменена; seed теперь фиксирован.
- Контракт изменён на BITGET_NATIVE_260_CLOSED_BARS_V2. Прежний V1 и архивный expanding-prefix не разрешают CONFIRMED. Исторические результаты не пересчитаны и не становятся статистикой нового live-контракта.
- Исключение при записи/инвалидации могло завершить background task, сохраняя успешный HTTP health. Теперь цикл выдаёт безопасный статус и повторяется с ограниченным backoff; CancelledError сохраняется. Завершённая задача даёт health 503. Health остаётся проверкой жизни процесса, а не доказательством свежести рынка.
- Частично неработающие TF теперь видны в owner API/UI. Рабочие TF продолжают наблюдаться. Выключенный/остановленный наблюдатель и ошибки не показывают активные сценарии и не выдают alerts.

## Воспроизводимые входы

На первом успешном наблюдении нового cutoff атомарно с watermark и событиями сохраняются:

- точные **разобранные** 260 native OHLCV, Bid/Ask/last, timestamp котировки и время получения;
- первое время обнаружения, funding-ответ и все BASE hypotheses, включая пустой список;
- model SHA-256, input contract и SHA-256 канонического JSON; каждое событие связано с input_sha256.

Это не сырые байты HTTP-ответа и не криптографическое доказательство происхождения от биржи. Самосогласованный поддельный набор можно перехешировать; аудитор отдельно проверяет воспроизводимость планов. Время и задержки обнаружения влияют на применимость entry, поэтому воспроизведение плана не означает исполнение next-open в Demo.

SQLite хранит максимум 2048 входов на TF (~7 дней при полном 5m-сборе). Экспорт нужно архивировать до удаления старых записей. complete_history_claimed всегда false; earliest_retained_seq, has_more и глобальный sequence явно показываются. Разрывы sequence между TF допустимы; аудитор проверяет пропуски **cutoff** внутри страницы одного TF. Он не доказывает непрерывность между разными страницами или полноту до/после выгрузки.

Owner-only GET `/api/hunter/inputs?frame=5m&after=0&limit=20` экспортирует до 100 записей. Для продолжения использовать next_after при has_more=true. HTTP Basic, no-store, CSP и read-only middleware сохранены. Экспорт не создаёт внешних запросов и не меняет допуск стратегии.

Офлайн-аудит сохранённой страницы:

```bash
python -m scripts.hunter6_audit_inputs path/to/5m.json
```

Проверяются hash, модель/контракт, последовательность, непрерывность 260 баров, cutoff и свежесть котировки при обнаружении. Все BASE планы заново вычисляются из этих входов и сравниваются целиком. Проверка не рассчитывает прибыльность, не объявляет independent OOS и не заполняет eligibility.json.

Один ограниченный публичный сбор с сохранением точных входов:

```bash
python -m scripts.hunter6_capture path/to/capture
```

Команда выполняет ровно один цикл, ограниченный 45 секундами, создаёт временную отдельную SQLite и закрывает клиента. Нет сервиса, планировщика, аккаунта, ключей биржи или ордеров. Ошибочные TF сохраняются как ошибки с пустыми входами; CLI завершается ненулевым кодом. Это не длительный forward-run.

## Фактические доказательства

В `native_probe/` сохранён один публичный цикл 30 октября, четыре точных окна: 5m, 15m, 1h, 4h. Повторное вычисление всех четырёх совпало, один технический LIQUIDITY_SWEEP на 4h был отклонён по условиям входа; итог NO TRADE, alerts 0, orders 0. Это конкретная выборочная проверка транспорта/воспроизведения, не доказательство частоты возможностей или качества сигналов. Предыдущая короткая проба хранила только итоги; эти файлы сохраняют и разобранные входы.

Сетевой прогон использовал стандартный прокси среды, с socksio только во временном окружении агента. requirements.txt, ci/requirements.lock и production не менялись.

## Code/security review

Отдельный проход: источник остаётся фиксированным публичным Bitget GET allowlist, без redirects/торгового клиента. Экспорт защищён owner, frame и размер страницы ограничены, SQL параметризован, секреты/сырые исключения не публикуются. JSON в UI выводится через textContent. Удержание входов ограничено, watermark переживает pruning/restart. При невалидном JSON/NaN транзакция откатывает и watermark, разрешая восстановить запись. Старые события другого input contract не показываются активными.

Открытых критических/высоких дефектов в изменённом пути при этом проходе не обнаружено. Ограничения: независимого преимущества нет, котировки/исходы модельные, входы unsigned, непрерывного server-forward и физического Android нет. SQLite требует отдельного постоянного хранилища для длительного запуска. Существующий runtime Aura 5.0, Render, production, PAPER/Active43 и торговые команды не менялись.

Результаты финального полного локального и exact-head CI-прогона — в VERIFICATION_RU.md и описании PR #65. Старый вердикт NO_EDGE_FOUND сохранён.
