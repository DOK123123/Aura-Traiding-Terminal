Только виртуальные средства. Проверка проведена от main после PR #21.
PAPER и расписание в рамках этой работы не включались. Merge, deploy, запись
production SQL, изменение секретов, счетов Aura 4.2 и Paper Practice не выполнялись.
Численные результаты и ссылки: `AURA43_AUTONOMY_RESULTS.json`.

Итог: **CODE_READY=TRUE, PAPER_ONLY=TRUE, OPEN_CLOSE_TESTED=TRUE,
SCHEDULER_READY=TRUE, PRODUCTION_READY=FALSE**. Первые статусы относятся к коду и
изолированным проверкам; реальное расписание и автономный production OPEN/CLOSE
ещё не подтверждены. Python: **1513 passed, 2 skipped** (отдельные opt-in проверки
старых Auto42/Practice); JavaScript: **208 passed**. Active43 PostgreSQL выполнен:
7 сценариев исполнения, 12 групп SQL-проверок и 2 полных native LONG/SHORT цикла
через настоящий scheduler CLI. Единственное предупреждение — существующий
Starlette/AnyIO DeprecationWarning.

Нормальный `/tick` действительно вызывает торговый Service, а не diagnostics.
GitHub job с event `schedule` и разрешением `true` выбирает CLI без diagnostic/OFF
флагов. Ручной `tick/saved_mode` выбирает тот же путь. Оба соблюдают сохранённый режим
и никогда не переводят OFF в ON. Ручной `tick/off_only` — отдельная безопасная
проверка сохранения; она не доказывает работу стратегии или торговый OPEN/CLOSE.

## Исправленная ошибка

Сервер может успешно сохранить PAUSED-решение при отказе рынка. Старый CLI считал
любой `status=PAUSED` неизвестным исходом, скрывал причину и повторял тот же уже
сохранённый tick. Теперь после проверки идентичности, paper-only флагов, границ
счётчиков и `state_saved=true` он один раз сообщает `tick safely blocked` и безопасный
код причины, завершаясь с кодом 1. Немедленных повторов нет; следующий период
расписания может повторить получение свежих данных через существующее recovery.

Это не превращает PAUSED в успех, не снимает риск-лимиты и не включает ON.
Некорректный/чужой/неподтверждённый ответ не получает отметку о сохранённом решении.
Причины печатаются только из allowlist; сырой ответ и секреты не выводятся.

## Что реально проверено

### Изолированная среда

- Обновлённый PostgreSQL runner выполняет **реальный CLI GitHub scheduler → ASGI
  HTTP API → нативный Bitget adapter на тестовых OHLCV → индикаторы → сигнал →
  Paper Engine → настоящий локальный PostgreSQL → owner status** для LONG и SHORT.
- HTTP wire — локальный ASGI adapter, RPC wire — adapter к настоящим SQL-функциям.
  Это не проверка публичной сети, hosted PostgREST или production Supabase OPEN/CLOSE.
- Дополнительно проверяются SL/TP, одновременное касание, независимый пересчёт PnL,
  комиссий и проскальзывания, DB restart, неизвестный исход commit, конкурентные
  контроллеры, outage/recovery, RLS и неизменность старых счетов/SQL-функций.
- Новые проверки: STOP/EMERGENCY через owner API при ожидающем входе и открытой
  позиции для LONG/SHORT, рестарт, обычный scheduler `/tick`, конкурентный повтор,
  сохранение запрета входа и защитного закрытия; STOP отменяет право автоматического
  восстановления после market outage.
- Исходные тесты causality сравнивают сигналы на префиксах данных и после добавления
  будущих свечей; данные для входа только закрытые. Параметры стратегии не подбирались.
- Все синтетические сделки остаются в disposable БД с `--network none`, без портов,
  памятью 512 MiB и 1 CPU. Production DSN/ключи runner не принимает.

Воспроизведение из корня репозитория с установленными requirements и Docker:

```bash
python -m scripts.verify_active43_postgres --output /tmp/active43-autonomy-new.json
AURA_ACTIVE43_VERIFY_POSTGRES=true python -m pytest -q
node --test tests/*.cjs
```

Первый путь должен быть новым файлом. Runner запрещён при `RENDER` и при `python -O`.
Образ PostgreSQL 16 закреплён digest; существующие контейнеры/production БД не используются.

### Реальный рынок и Render

- Локально прочитано полное окно реальных публичных 15m свечей Bitget через тот же
  `Market.snapshot`, рассчитана текущая стратегия. Результат и UTC cutoff в JSON.
  Это не подтверждение полного окна именно с Render.

  отсутствие свежего heartbeat при выключенном расписании; оно не исправляется
  сбросом счёта и не является доказательством неисправности торгового движка.
  GitHub job success означает доставку диагностики, а не общий readiness PASS.
- Ранее [#24 на main](https://github.com/DOK123123/Aura-Traiding-Terminal/actions/runs/39417473462)

1. Проверить PR и результаты, затем владелец может выполнить Merge.
2. **Render redeploy не требуется:** меняются только scheduler CLI, локальные тесты,

## Включение PAPER — только после отдельного разрешения владельца

### Сначала подтвердить расписание с OFF-счётом

1. В [GitHub Variables](https://github.com/DOK123123/Aura-Traiding-Terminal/settings/variables/actions)
   установить существующую `AURA_ACTIVE43_BITGET_SCHEDULER_ENABLED` в `true`.
   Сам режим Paper в терминале пока оставить OFF.
2. В [Actions](https://github.com/DOK123123/Aura-Traiding-Terminal/actions/workflows/aura-active43.yml)
   дождаться двух последовательных запусков **event=schedule**, а не manual diagnostics.
   Ожидание обычно 5–10 минут, GitHub может задержать запуск. Ожидать
   `tick confirmed`, mode OFF, opened=closed=0; диагностика вскоре после tick:
   Scheduler ACTIVE, Bitget/Supabase CONNECTED. При сбое не включать PAPER.

### Затем разрешить виртуальные входы

1. Открыть [терминал](https://aura-traiding-terminal.onrender.com/#active43-panel),
   раскрыть блок **AURA 4.3 ACTIVE PAPER**, войти владельцем и обновить состояние.
   Убедиться, что это Bitget и отдельный сохранённый счёт, а scheduler свежий.
2. Нажать **START EXPERIMENTAL PAPER** и явно подтвердить. Сервер заново проверит
   полное окно рынка, конфигурацию, риск и revision и только затем сохранит ON.
   Никаких искусственных сигналов не требуется. Отказ START нельзя обходить.
3. Закрыть браузер. Actions продолжает вызывать backend; следить за event=schedule,
   timestamps, SIGNAL/DECISION, затем естественными OPEN/UPDATE/CLOSE. Отсутствие
   сигнала допустимо. Первый tick после START не обязан немедленно открыть сделку:
   causal модель ожидает закрытый сигнал и следующий доступный бар исполнения.

Для явного ручного торгового цикла после разрешения: `operation=tick`,
`tick_policy=saved_mode`. Он соблюдает текущий ON/OFF; это не кнопка START.
`off_only` должен отказать при ON или открытой позиции — так и задумано.

Подтверждение полного production-цикла: owner `/api/active43/journal` и история
показывают связанные ID OPEN/UPDATE/CLOSE, правильный источник Bitget, времена,
комиссии/PnL; повторное чтение после рестарта возвращает тот же счёт/позицию/историю.
Не выдавать TEST_ONLY/локальные сделки за эти события. При ошибке commit с неизвестным
исходом сначала читать receipt/состояние; не создавать новый искусственный сигнал.

## Аварийное отключение

1. В Owner-блоке нажать **STOP · запрет новых входов**. Это сохраняет OFF и отменяет
   ожидающие входы. Для постоянной блокировки новых входов — **EMERGENCY STOP**:
   сохранится EMERGENCY; автоматически она не снимается, START будет запрещён.
2. **Если позиция открыта, оставить scheduler работающим:** STOP/EMERGENCY не являются
   немедленным CLOSE; старые виртуальные SL/TP продолжают обрабатываться только
   работающими ticks. Не отключать backend/расписание как замену защитному выходу.
3. После подтверждённого отсутствия позиции/ожидающих операций можно установить
   GitHub variable обратно `false`. Уже исполняющийся запрос этим не отменяется;
   защитой остаются сохранённый OFF/EMERGENCY и транзакции БД. Не удалять строки,
   не сбрасывать счёт и не снимать emergency прямым редактированием SQL.

Если Supabase недоступен, нельзя считать STOP/EMERGENCY сохранённым: требуются
успешный ответ и повторное чтение. Отключение GitHub variable остановит будущие
плановые вызовы, но не уже начавшийся tick и не является подтверждением выхода из
позиции. Ручные ticks и иные авторизованные источники вызова также не блокируются
одной GitHub variable. При недоступном backend до восстановления невозможно
гарантировать обработку виртуального SL/TP. Реальных ордеров при этом нет.

## Ограничения и критерии допуска

Код технически проверен для экспериментального Paper; прибыльность не доказана
(`UNVALIDATED_FUTURES` / NO_EDGE_FOUND). Funding не моделируется. Исполнение —
симуляция по закрытому OHLC/следующему open, а не реальный биржевой fill. При SL и TP
в одной свече выбирается SL; внутрисвечная последовательность неизвестна.

GitHub cron — best effort; возможны задержки и пропуски, а в неактивном публичном
репозитории расписание может отключиться. Бесплатный Render может засыпать/просыпаться
с задержкой. Вызов каждые 5 минут не доказывает 24/7 и не создаёт SLA. На простое
SL/TP не исполняется: это виртуальные условия, а не стоп-ордера на Bitget.
При catch-up старые свечи используются для защиты, но не для задних входов.

Оставшиеся ограничения production-проверки: выключенное расписание, отсутствие
разрешения ON, отсутствие естественного автономного OPEN/CLOSE и измеренного
периода непрерывной работы. Критических новых ошибок ядра этим аудитом не выявлено.
Перед началом эксплуатации нужны owner-authorized schedule-проверка и START;
до них `PRODUCTION_READY=FALSE`. В рамках задачи они не выполняются.
